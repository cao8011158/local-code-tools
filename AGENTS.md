## Jedi evidence requirements

Read the [capability experiment and official-document comparison](review/jedi-capabilities/README.md), [case matrix](review/jedi-capabilities/CASE_MATRIX.md), and raw observations before claiming a Jedi limitation or adding special handling. The audit records Jedi 0.20.1 / Parso 0.8.7 on Python 3.12.14; it is a finite set of experiments, not all Python boundaries and not a production admission whitelist.

- Use the applicable public Jedi API and consume its output by its documented meaning. Do not pre-emptively reject callbacks, containers, descriptors, aliases, closures, decorators, imports or other ordinary syntax because a form is untested or might be difficult. No second target inference, comparison, filtering or override chain.
- A new limitation claim needs the exact captured sources/imports, version/settings, API, line/character column, raw result or exception, a minimal reproducer and normal control, and a link to the relevant official documentation. First check missing inputs, project paths, query position, API selection and our mapping. Distinguish officially documented limits, reproduced but unexplained observations, our integration defects, and unverified questions. General documentation is not official confirmation of a specific bug.
- Preserve separate observations at supplied arguments, assignment RHS values, return expressions and final calls. JEDI-CAP-04 shows that Jedi can identify an assigned/passed function while the final dictionary call returns no target. Use those observations for source/update dependencies and preserve the original Jedi call evidence.
- JEDI-CAP-01/02 have successful direct and cross-module callback/getter/container examples. Empty results in dict_register, alias-write or separate-writer cases apply only to those precise samples. They do not justify a feature-wide unsupported rule. An untested form still goes to Jedi normally.
- JEDI-CAP-03 requires correct API/context selection: classmethod value inference may identify a descriptor while get_signatures identifies its declaration. JEDI-CAP-06/07 require preserving instance/abstract callable results, multiple results, duplicates, lambda positions with no full_name, external paths and stubs without silently relabelling them as concrete functions or constructors.
- Reproduced metadata issue: recursive_parameters and mutual_recursive_parameters return the correct signature target, then Signature.params raises RecursionError. Keep the target and record the metadata gap. Reproduced configuration issue: fast_parser=False with a path-bearing Script can raise KeyError in this dependency combination; the code-only control can work. API exceptions are not empty target results. Neither exact issue was verified as officially acknowledged; see raw follow-ups and the documentation comparison.
- The user authorized the [bounded callback and container supplement](review/parser-refactor/BATCH2_SOURCE_ASSOCIATION.md). It may use captured source records to associate an exact supplied argument or dictionary entry with a final call only when Jedi returns no names and no error. Jedi still supplies the callable definition. Preserve the raw empty call result and record the separate source association. Ordinary misses, errors, and any nonempty result bypass this lookup. Other gaps remain unknown pending independent evidence and explicit scope. Keep source recording and incremental scheduling separate from target decisions.
- This documentation audit does not certify LCT's final-consumer-to-original-provider dependency wiring or its incremental propagation. Those are our responsibilities and remain separate open implementation work. Do not call missing source edges or overly broad scheduling a Jedi capability limitation.
