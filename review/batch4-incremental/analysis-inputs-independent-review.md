## 这次完成了什么

已有五类成功读取和容器 writer 订阅确实已被使用，本次没有将它们误报为未接线。缺口之一是：Jedi 没找到目标、报错或命中缓存时，也需要知道它当时可参考哪些捕获源码。

`Analyzer.query()` 现在在缓存和推断分支之前统一登记输入范围。已认证的 v6 捕获使用精确导入组件；没有这项证明时，显式记录全捕获范围。成功、空结果、错误和缓存走同一个入口，原始目标、UNKNOWN、推断记录、调用证据和效果语义不变。

新增 `AnalysisInputs` 把范围、成员、使用者分开保存。同一个组件的成员只存一次，不按每个使用者复制。范围 ID 根据有序模块身份生成；每个使用者只登记一次；独立 20,000 条记录预算覆盖三类记录，超限原子放弃本次新增并标记截断。这不是旧 analysis_reads 预算的同一份限额，也不是完整依赖证明。

三组记录持久化到私有 SQLite。`FileDependencies.input_scope_readers()` 按变动文件的成员索引定位范围，再沿使用者索引取结果；宽范围使用者在每次构建开始只加入队列一次。`prepare()` 实际消费反查结果，保留原 v6、值流和旧依赖门禁。缺失、旧格式或截断的新证据拒绝用于复用。局部合并替换选中使用者的记录，保留已验证的其他记录，并检查跨选中边界；相同 Python 捕获复制原记录。旧版本不原地修改。

manifest 仅含 schema、partial coverage、数量和截断标记；完整范围不进入 manifest、状态回复、公开节点、向量或 Neo4j。

## 访问范围与提交前修正

初稿在每次登记前重复检查组件成员，合并和校验也逐使用者扫描整个范围目录。主 Agent 给出明确修正后，成员验证/排序/哈希只在首次准备时发生，计数为 O(1)，合并和校验按范围分组一次处理。

另有模块身份校验最初读取全部节点 JSON。现已按范围实际引用的模块 ID，每 256 个批量查询 `node_id,repository,path` 独立列，使用主键定位；空 payload 不查 catalog。开发测试验证实际绑定 ID、没有读取 data 列和未知模块拒绝。

| 独立检查 | 结果 |
|---|---|
| 真实 Jedi 空结果、后端异常、缓存和重复查询 | 统一登记；相同组件的后续查询禁止重新枚举成员仍通过 |
| 100 成员、100 使用者 | 1 个范围、100 成员、100 使用者，共 201 条；开发 200/200 对照共 401 条 |

实际 SQLite 反查的 `EXPLAIN QUERY PLAN` 在 0、20、100 组无关范围下均为两个覆盖索引 SEARCH，无 SCAN，每次一条 SQL、一个使用者。首次/重复 VM 步数分别为 26/19/19、27/20/20、27/20/20；静态程序均 18 条指令，固定一成员一使用者的测试保持在 36 步预算内。原先“不同规模必须完全相同 VM 步数”的断言过严，初次因此 7 passed/1 failed，原测试和日志保留；改为相同计划与固定工作量指令上界，不修改生产来追求单步一致。此证据不声称整个 build O(1)：输入捕获、完整性验证、输出新快照仍有必要的全量准备/序列化成本。
