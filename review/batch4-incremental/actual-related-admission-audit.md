`Graph.import_request_module(scope, stmt, alias)` already normalizes a relative import against the importing module's qualified name, including the package initializer rule; `Graph.imported(repository, normalized_name)` then applies the existing local-first/pinned resolver. For `service.py:13`, it gives `trpg_state_machine.availability`, whose captured module and `AvailabilityRuntime` export are present. For `item_package.py:6`, it gives `trpg_state_machine.item_units`, whose captured module exports `valid_item_unit`. In contrast, `dnd_runtime.py:3` normalizes to `trpg_state_machine.rules_adapter` but returns `boundary:external-or-excluded:trpg_state_machine.rules_adapter` in this **partial** fixture. Treating that boundary as a captured module would be false evidence. The current `_certify_v4`, `_certify_common` and `component_policy` inspect only `stmt.module` after rejecting `stmt.level`; they do not reuse the resolver's normalized request.

The smallest justified production step for the import barrier is to use `Graph.import_request_module` for each top-level `ImportFrom` in `_certify_v4`, `_certify_common` and `component_policy`, then require one actual captured/pin-authorized target AST, exact exported names, and a connected importer/provider edge. Keep star/invalid-level/missing-target imports rejected; do not convert external-or-excluded into a provider. That step is sufficient to normalize the **known** `.availability` and `.item_units` relationships, but it is **not sufficient** to admit this nine-file capture. A subsequent local update involving any of the six complex files needs a separate complete read/producer/candidate-site witness or tightly specified additional syntax/effect rules, plus old-view and independent full-oracle checks; merely widening imports would violate the whole-capture gate.
