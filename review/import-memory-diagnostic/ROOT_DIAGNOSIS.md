## 结论

检查范围内没有发现“每写一条边就重新扫描全图”或重复写入同一输入记录。关系端点使用唯一索引定位。存在多轮线性准备和可避免的幂等重试准备；真正的数据库事务内存会累积各批修改，最终还接收整块分析证据。这些代码组织方式决定了 Neo4j 要承担的工作量，并非与我方代码无关。

不能声称已精确定位此前真实图 716.8 MiB 超限的各部分占比。原 `/tmp` 完整图已不在当前环境；本次保留旧证据，重新测量使用明确标注的合成数据，没有冒充真实图复验。

## 1. Python 准备与写入次数

直接执行未修改的 `Neo4jGraph.import_snapshot()`，用计数列表及假 driver 统计；未执行 SQLite load_snapshot、真实 Cypher 或数据库内存测量。分别检查新建及 already_present=true。

| 输入 | 节点记录访问 | 边记录访问 | 新建节点写入 | 逻辑边写入 | 原生关系写入 |
|---|---:|---:|---:|---:|---:|
| 100 节点 / 500 内部边 | 800 | 5,500 | 100 | 500 | 500 |
| 1,000 节点 / 5,000 内部边 | 8,000 | 55,000 | 1,000 | 5,000 | 5,000 |

两组均断言各类别写入 ID 无重复。节点输入被遍历 8 遍、边输入 11 遍，包括完整指纹序列化、合法性/唯一性检查及按类型分组。5 类节点与 7 类关系的分组各自重复扫描输入；类别数固定，所以在该输入上是线性增长，不是 N²。可以单次分组减少重复准备，但不能删除指纹/唯一性校验来制造提速。

一个逻辑边另存为 LCTEdge 节点，内部端点存在时再建立原生关系。两种表示承担原始证据查询及图遍历，不是同一批被循环重复导入；额外存储成本仍然真实存在。

**B3-006，P2，导入准备浪费：**`import_snapshot()` 在检查 Neo4j 中相同版本是否已经完整存在之前，先建立所有 node_batches/edge_batches/relation_batches。1,000/5,000 的已存在分支仍遍历 8,000/55,000 条记录，并调用 17,000 次逐行 canonical，最后才返回 already_present，实际写入零条。这不是首次导入超限的已证实根因，但确实浪费。

最小修复方向（未实施）：保留输入身份、指纹、类型、唯一性等必须校验；将仅为写入准备的所有参数批次延后到事务获得同 scope/fingerprint 且 complete=false 的判定之后、第一笔节点写入之前。完整存在时跳过批次装配；缺失时仍在节点写入前验证所有行大小，失败依赖当前事务回滚。不可把数据库查询放到无事务保护位置后省略原有冲突检查。

此外，`payload` 完整 JSON 字符串和所有批次列表在导入期间仍由 Python 局部变量持有。它们影响 Python 端内存，不能直接当作 Neo4j 事务内存；本次未测 Python 峰值。可释放已完成哈希用途的 payload，并对分组准备做单次遍历；不据此承诺能解决数据库错误。

## 2. 原关系查询是否全图扫描

在 Neo4j 5.26.0 对原 CALLS 写入语句执行 EXPLAIN，以及单行 PROFILE 后回滚。两个端点均为 `(namespace, version, node_id)` 上的 NodeUniqueIndexSeek(Locking)，每个索引查找 1 次 DB hit，最终匹配 1 行。无 AllNodesScan/NodeByLabelScan。

执行计划虽然出现 CartesianProduct，但两边是由唯一约束保证的各至多一个端点，不是把两张全表相乘。其余关系类型使用同一形状语句，未逐一 PROFILE；不将这一条计划扩大为所有环境、所有查询的证明。

## 3. 实际数据库分阶段内存

同一自有 Neo4j 进程，Java 最大堆 1 GiB，配置 pagecache 128 MiB；四组合成数据，分别使用独立 namespace。所有导入成功，服务在约 21.87 秒后正常关闭。观测字段为 SHOW TRANSACTIONS 的 estimatedUsedHeapMemory，属于事务保留内存估计，不是总 JVM RSS，也未捕获提交过程每一瞬间的峰值。

| 输入 | 节点写完 | 逻辑边写完 | 原生关系写完 | 最终 graph_json 写完 |
|---|---:|---:|---:|---:|
| 100 节点 / 500 边，小证据 | 2 MiB | 2 MiB | 4 MiB | 4 MiB |
| 1,000 节点 / 5,000 边，小证据 | 4 MiB | 20 MiB | 26 MiB | 26 MiB |
| 100 节点 / 500 边，8 MiB 重复字符证据 | 2 MiB | 2 MiB | 4 MiB | 约 20 MiB |
| 100 节点 / 500 边，61.16 MiB 重复字符证据 | 2 MiB | 2 MiB | 4 MiB | 约 126.3 MiB |

明确发现：最终 `SET s.graph_json=$graph` 一次传递完整证据，不受 `_batches()` 的 1 MiB 参数批次限制。大字符参数的确可以单独明显增加事务保留内存。原图实际为 61.16 **MB**，合成为 61.16 **MiB** 且结构不同/高度可压缩；不能把表中126.3MiB套用到真实图，也不能据此推算真实图总峰值。该测试没有复现此前真实图失败。

本次没有增加 Neo4j 堆、关闭内存保护或更换导入事务语义。

## 4. 建议与边界

- 不再把问题仅归因于“数据库太小”：我方单事务、全部参数预装配和整块证据属性都会增加内存需求。
- 没有证据支持按“逐边全图扫描”去重写查询；已观察到正确的索引定位。
- 可以先修正幂等重复准备及 Python 中不再需要的大对象保留；这些优化不能保证解决 Neo4j 事务峰值。
- 长期分批事务＋未完成版本隔离＋验证后发布能限制累积修改，但需另行明确失败重试、清理、并发和完整性契约；不能只更改每批条数。
- 分析证据应单独评估分记录或分块存储，使查询与写入能够有界，不能遗漏 UNKNOWN、原因或身份信息。
- 若需要确定现有真实图的准确阶段增长和峰值，必须先恢复/重新生成同一固定源码结果，再做有界实测；本轮没有悄悄重建。
