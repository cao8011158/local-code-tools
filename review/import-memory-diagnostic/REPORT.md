# Bounded Neo4j import memory diagnostic

Source: exact `lct/neo4j_graph.py`, `common.py`, `__init__.py` from remote SHA `4557d4cd2c5a6b33933b3832f81dfb64207e4e4b`, implementation `42b0`. This diagnostic invokes the unmodified `Neo4jGraph.import_snapshot` with synthetic snapshots. A stub for `lct.storage` deliberately raises if `load_snapshot` is called; the diagnostic therefore **does not measure SQLite loading, real manifest validation, or a real user graph**. It uses one owned Neo4j Community 5.26.0 process, 1 GiB max JVM heap, configured 128 MiB page cache, with unique diagnostic namespaces in the existing local test database. The process was terminated cleanly (exit 0) after 21.87 seconds. No production code or existing scopes were modified.

`SHOW TRANSACTIONS YIELD *` from a separate session sampled `estimatedUsedHeapMemory` at transaction phase boundaries and a bounded set of batch boundaries. This is Neo4j's estimated retained transaction heap, rounded in allocation increments; it is neither Python RSS nor total JVM heap. All four synthetic imports committed successfully.

| Synthetic input | Canonical bytes | After node writes | After edge writes | After native relations | Before final graph property | After final graph property |
|---|---:|---:|---:|---:|---:|---:|
| 100 nodes, 500 edges, tiny evidence | 51,209 | 2 MiB | 2 MiB | 4 MiB | 4 MiB | 4 MiB |
| 1,000 nodes, 5,000 edges, tiny evidence | 528,509 | 4 MiB | 20 MiB | 26 MiB | 26 MiB | 26 MiB |
| 100 nodes, 500 edges, 8 MiB repeated evidence | 8,439,817 | 2 MiB | 2 MiB | 4 MiB | 4 MiB | 20 MiB + 120 bytes |
| 100 nodes, 500 edges, 61.16 MiB repeated evidence | 64,182,117 | 2 MiB | 2 MiB | 4 MiB | 4 MiB | 132,456,240 bytes (about 126.3 MiB) |

This isolates two concrete retained-memory components. The single transaction keeps node/edge/native-relation writes until commit, increasing from 4 MiB to 26 MiB in the larger modest case. Independently, the final `SET s.graph_json=$graph` carries the entire evidence JSON in one parameter, outside the 1 MiB `_batches` cap, and raised transaction heap by about 122 MiB for the 61.16 MiB repeated-string fixture. Python canonicalization also creates full payload and graph strings; its peak RSS was not measured. The fixture's repeated `x` is highly compressible and has none of a real graph's object diversity. The canonical payload is 64.18 MB decimal, whereas the cited real evidence size around 61.16 MB has a different unit/shape; these cannot establish that the real import fits a 1 GiB heap or reproduce its failure.

The **exact original** CALLS native-relation statement was `EXPLAIN`ed after schema creation and `PROFILE`d for one row inside a rolled-back transaction. It uses two `NodeUniqueIndexSeek(Locking)` operators on the `(namespace, version, node_id)` uniqueness constraint. A `CartesianProduct` operator is present between those singleton endpoint seeks, but the one-row profile shows one output row and one DB hit per seek. No `NodeByLabelScan` or `AllNodesScan` appears in that observed plan. The CartesianProduct label alone is thus not evidence of a per-edge full-graph scan. Other `REL_TYPES` use the same statement shape but were not individually profiled. Plan and raw phase observations are in `results.json`.

The import prepares all parameter batches before its first write, then does five passes over all nodes by kind and multiple passes over edges by relation kind; these are linear whole-input traversals, not repeated whole-database scans per edge. The 1 MiB batch limit bounds individual node/edge/relation parameter batches, but the graph property and the transaction lifetime remain unbounded by that limit (subject to the 128 MiB canonical snapshot limit and graph caps). The synthetic observations support substantial transaction retention and a large final parameter as plausible causes, not a definitive diagnosis of the unavailable real database's memory failure. No real-data run or full-scale 50,000/500,000 run was performed.

Reproduce with `/workspace/scratch/413372d9a5a5/lct-round5-review/.venv/bin/python review/import-memory-diagnostic/diagnose.py` from this project root, only when the local Neo4j service is stopped; it owns the service process and creates new unique scopes. The driver wrapper observes after consumed statements and does not rewrite any import statement. The script has a 175-second between-case deadline and a 45-second startup bound; a supervising process timeout with termination cleanup is appropriate if reproducing in another environment. Existing diagnostic scopes remain for postmortem inspection.
