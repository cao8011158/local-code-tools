## Repair

`Graph._receiver_context` now follows cached AST/catalog parent identities from a method, returned lambda or nested function to its nearest declaring class. It traces a free receiver, `super`, or `__class__` through simple local cell assignments (`receiver=self`) and definition-time default bindings (`lambda receiver=self`) into the actual nested execution owner. It inspects nested definition headers in their enclosing scope while keeping nested bodies separate. The method's first parameter establishes the receiver unless it is a direct `@staticmethod`; nested parameters, assignments, local imports, global declarations and nested definition names can shadow a captured receiver. An intervening nested function binding prevents attribution to the declaring method. It emits a separate `class-receiver-context` source support from class to the actual closure owner with `via_method` detail even when the initial base is UNKNOWN. The indexed source-reader closure therefore selects the lambda and replaces its own site/edge/source records. The outer method's nested body is not treated as a substitute for analyzing the lambda.

`tests/test_definition_context_dependencies.py` asserts both returned lambda and nested function source supports under an unresolved base, an aliased/default receiver and the enclosing method identity, and absence of supports for parameter-shadowed lambdas or a direct staticmethod parameter. A public warm/fresh oracle proves the alias closure target and all semantic source tables. `docs/INCREMENTAL_UPDATE.md` states the bounded source-site and closure relation. No public `CALLS` relation, frontend target precision, core dependency version, paid provider, business execution or Neo4j behavior changed.
