# Function-value dependency contract (proposed)

Status: broader design contract; a narrow dictionary value-flow slice is now implemented as described in [incremental update status](INCREMENTAL_UPDATE.md#function-value-dependency-design-status). The earlier source baseline is preserved in [the Batch 4 audit](../review/batch4-incremental/FUNCTION_VALUE_GAP_AUDIT.md). The full contract below is not an implementation claim.

## Scope and invariants

The goal is to explain and maintain call targets that flow through Python values: assignments, arguments, returns, closures, dictionaries, instance fields, decorators and registrations. Reuse the existing function definition nodes, including methods and lambdas, as callable targets. A call expression has one source identity and zero or more candidate targets, possibly with `UNKNOWN`. An aggregate `CALLS` relation from the execution owner to a function is a projection of independently supported source sites; a reference or registration is not itself an invocation.

For a fixed capture of source bytes, configuration, dependency pins and analyzer version/declared precision, an accepted incremental build must yield the same public nodes, edges, call sites, target sets, uncertainty, completeness, provenance and relevant semantic fields as a fresh full build of that capture. Compare identities after required capture rebinding; this is not permission to ignore a meaningful identity difference. Diagnostics, work counters, timing, publication timestamps and report presentation need not match. If an implementation cannot prove semantic equality, it falls back to full analysis. A full build can itself be imprecise; the graph must retain its `UNKNOWN`/boundary evidence and never infer completeness from a newly created graph node. The target is sound preservation relative to the full *current* analyzer under fixed inputs, not full runtime Python precision. Scope excludes dynamic execution fidelity, exact loop invocation counts, and modeling every literal, variable or runtime object as a node.

## Identity and evidence

| Concept | Proposed identity/evidence | Important distinction |
| --- | --- | --- |
| Callable definition | Existing catalog function node, with capture/version identity as applicable | Lambda has its own function node; a bound method carries a receiver binding without duplicating the definition. |
| Abstract container | Stable allocation/origin identity plus context sufficient to distinguish instances; aliases to the same container share identity | Different containers must not share an entry merely because their keys match. A standalone dictionary graph node is optional. |
| Storage entry | `(abstract container identity, key equivalence class)` for a known key; similarly scoped field identities where modeled | Unknown key in a known container is a range subscription over its entries, **not** a literal key. Unknown container identity is a separate uncertainty. |
| Write / assignment | Stable source site, control-flow context, storage position and candidate value/target supports | Multiple reaching definitions coexist across branches, loops and aliases; no single latest-target overwrite. |
| Read / call | Stable source site, binding/entry read, target candidates and their supporting producer paths, plus unresolved reasons | The call site is distinct from the execution owner and the callable target. Optional loop metadata does not claim an invocation count. |

Key identity must respect Python equality and hashing for supported constant primitive keys. In particular `True`, `1` and `1.0` can address the same dictionary entry; naïve type tags would split them incorrectly. Specify and test the supported constant-key equivalence/canonicalization before persistence. Opaque user-defined `__hash__`/`__eq__` cannot be evaluated by running captured project code; keep their possible aliasing uncertain. Dynamic keys and ambiguous container origins retain subscriptions or `UNKNOWN` rather than pretending to be exact entries.

Provenance is many-to-many. A supported call target may depend on a write, argument binding, default, return, registration and lookup; one source can support several targets and several independent sources can support the same target. Deleting or changing one support removes only its contribution. Projected owner-to-target `CALLS` edges are recomputed from surviving call-site supports, including the target status and uncertainty; they are not the authoritative dependency record.

## Value-flow obligations

Track parameter and keyword binding at actual calls, defaults evaluated at **definition time**, return flows and nested closures. A closure captures binding/cell semantics: a later rebind can matter, so copying the value at function creation is not generally valid. Preserve receiver identity for bound instance methods while distinguishing an ordinary function accessed on a class from an instance-bound method; account for `functools.partial` argument binding, decorator application and wrapper results, callback registration and higher-order calls. These are obligations to propagate or conservatively mark uncertain, not a declaration that every form is already implemented. A dynamic attribute/subscript lookup, reflection, escaped container, dynamic import or unknown external callback must keep its boundary/unknown state. Model the events and relations needed for precise invalidation without requiring a persistent graph node for each temporary value.

Control-flow joins retain possible reaching writes. A conditional write does not universally kill the earlier target; a loop can revisit a site without adding a static call site per iteration. Deletions, dict copies/unpacks, aliasing, positional/keyword expansion and field mutation require explicit ordering and applicability proofs before a prior value can be excluded. A read of a missing key may depend on a **future** writer, even when no producer exists in the previous capture.

## Reverse dependencies and update admission

Record both successful and unsuccessful reads. For an exact entry, retain the producer supports actually inspected, the candidate set and membership decision; for a known-container unknown-key read, retain the container range; for an unbound name or missing key, retain the prospective namespace/key membership subscription. Broad uncertainty needs a separately identifiable universe. Reads must include paths through arguments, returns and closures as well as current container-effects paths. Include captured source context, import resolution, configuration, runtime/analyzer policy and pin/cleanliness decisions when they can affect target selection.

On a change, compare old and new producers. A deletion needs the old snapshot's evidence to find its consumers; a new producer needs negative/membership subscriptions to find consumers that previously saw no candidate. Seed a reverse-index worklist with changed producer identities, memberships and contextual inputs; traverse consumers and newly produced output facts, including forward argument effects from changed call sites. Continue until the affected facts stabilize. Stop at a boundary only when *all* observable output facts are proven identical: candidate targets, absence/membership, `UNKNOWN`, completeness, edge/site fields and provenance included. Equal return types alone are insufficient. Cycles, missing old evidence, unsupported equality, incomplete subscriptions, budget exhaustion or incompatible contexts cause conservative expansion or full analysis. The analysis work should be indexed from known identities and actual relationships; output serialization, hashing and inventory may separately remain O(N) when the format requires it.

## Persistence and release gates

SQLite's immutable, captured snapshot remains authority. A future schema must declare versions and coverage for site/write/entry identities, support provenance, successful/failed reads, ranges and subscriptions, indexed reverse lookups, truncation and compatibility. Decide and document how these records bind across repository capture versions and how existing site and definition identities are rebound before enabling reuse. An old snapshot lacking complete compatible evidence must rebuild or fall back; a partial inventory cannot certify a negative dependency. Candidate publication must verify artifact integrity and preserve the previous current pointer on failure. Dense artifacts may be reused only through the existing compatibility and verification gates. Before exposing any new semantic node/edge kind, explicitly review graph projection, query behavior and schema/version compatibility. Storage, write and call-site nodes must not automatically receive embeddings or enter module/class/function search levels; node-to-vector cardinality need not be 1:1. Neo4j remains an optional projection of a published version, including unknown and boundary semantics; a graph migration is a separate pending gate, not part of this document. No implicit mutation or read-MCP write is authorized here.

Before implementation admission, test full-versus-incremental equality on cases for separate and aliased containers, equal Python keys, branch/loop reaching writes, missing/future keys, deletion, default timing, closures, returns, methods, partials, decorators and callbacks, uncertainty, old snapshots and failed publication. Show actual reverse-index plans and internal read counts under unrelated data growth; distinguish required O(N) serialization work. Use the current code and tests listed in the [gap audit](../review/batch4-incremental/FUNCTION_VALUE_GAP_AUDIT.md) as a baseline, then update the audit as implementation lands.
