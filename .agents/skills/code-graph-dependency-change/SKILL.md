# Code graph dependency changes

This is a repository-local instruction for agents working in this source tree. Start by reading [the design contract](../../../docs/FUNCTION_VALUE_DEPENDENCIES.md), [the current gap audit](../../../review/batch4-incremental/FUNCTION_VALUE_GAP_AUDIT.md) and [incremental-update status](../../../docs/INCREMENTAL_UPDATE.md). Check the actual source before treating any proposed design as implemented.

1. Identify current full-build behavior, the public site/edge fields, old snapshot evidence and the exact incremental admission gate. Separate existing coarse dependency coverage from missing reverse evidence. Reuse the catalog's function nodes, `EffectEvent` ordering/phase/conditional signals and current call-site evidence where possible.
2. For a proposed local change, enumerate successful and failed reads, producer/membership changes, aliases and uncertainty, including old evidence needed after deletion. Locate known identities by indexes and expand over actual relationships. Keep future-key/range subscriptions distinct from an actual dictionary key and preserve Python key equality for supported constants. Do not execute repository code to decide arbitrary `__eq__`/`__hash__`.
3. Accept incremental output only when it matches full analysis under the same captured inputs and declared precision for semantic nodes, edges, site targets, `UNKNOWN`, completeness and provenance. Normalize capture-rebound identifiers as required. Source supports, subscriptions and writes stay in the semantic comparison; candidate traversal and repeated identical gaps may differ, while distinct reason/location evidence must match. Owner execution-read/input ledgers need separate functional invalidation tests. For ordinary updates, incomplete proof requires safe local widening or explicit failure without publication, never automatic full analysis; UNKNOWN alone does not reject local updates. Full fresh analysis remains a test oracle.
4. Gate new persistence and projection on schema/version/coverage, rebinding, old views, failed publication and dense compatibility. Semantic nodes do not automatically enter search levels or receive embeddings. Preserve the SQLite authority, optional Neo4j boundary/unknown behavior and read-only MCP boundary.
5. Test the smallest meaningful case and an independent full-build control; show reverse-index plans/internal reads under unrelated data growth when performance is implicated. Keep serialization/inventory counts separate from closure traversal. Record source evidence, limitations and actual checks in the batch report.

6. For Jedi-backed call discovery, retain raw no-result, failed mapping, external boundary and exception evidence at the original site. Index mapped targets and literal lambda identity once per capture or selected-owner preparation; a matching name alone is not a caller relationship. Never admit every unknown call site separately for each function. Prefer a mapped Jedi target unless a concrete semantic counterexample and applicable source/effect proof justify excluding it. Distinguish query entry, cache hit, actual Jedi execution and candidate traversal in performance evidence.

If available in the agent environment, use `locality-review` for indexed-locality proofs and `batch-dev-review` when coordinating a user-authorized implementation batch. The gates above stand alone if those skills are unavailable. This file is committed/discoverable within the repository through `AGENTS.md`; it does not install a global ChatGPT skill or guarantee automatic injection into any current Work session.
